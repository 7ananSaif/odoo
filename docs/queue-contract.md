# Queue Contract — `invoice.agent` AMQP round trip

Pins the wire contract between the Odoo outbox, RabbitMQ, the aio-pika
worker, and the Odoo result consumer. Both sides must stay in lockstep with
THIS document, not with each other's code.

Topology source of truth: `invoice_queue/topology.py` (exchange, queues,
bindings, declaration order). Message schemas: this document.

---

## 1. Topology

| Kind      | Name                   | Type   | Durable | Binding / Arguments                       |
|-----------|------------------------|--------|---------|-------------------------------------------|
| exchange  | `invoice.agent`        | topic  | yes     | —                                         |
| exchange  | `invoice.extract.dlx`  | direct | yes     | dead-letter exchange for `invoice.extract`|
| queue     | `invoice.extract`      | —      | yes     | `extract.request`; `x-dead-letter-exchange=invoice.extract.dlx`, `x-dead-letter-routing-key=extract.dead`, `x-delivery-limit=3` |
| queue     | `invoice.result`       | —      | yes     | `extract.started`, `extract.done`         |
| queue     | `retry.5s`             | —      | yes     | DLX `retry.retry.5s`; `x-message-ttl=5000`, DLX back to `invoice.agent`/`extract.request` |
| queue     | `retry.30s`            | —      | yes     | DLX `retry.retry.30s`; TTL 30 000 ms, DLX back to `extract.request` |
| queue     | `retry.5m`             | —      | yes     | DLX `retry.retry.5m`; TTL 300 000 ms, DLX back to `extract.request` |
| queue     | `invoice.extract.dead` | —      | yes     | `extract.dead` on both exchanges           |

Declared idempotently by `invoice_queue/topology.py` and re-declared by the
worker after every robust reconnect.

### Retry ladder semantics (v0.9)

* The retry delay is the queue's `x-message-ttl` — expiry dead-letters the
  message back to `invoice.agent`/`extract.request`, re-entering
  `invoice.extract`. No worker timers.
* `x-delivery-limit: 3` is the crash safety net: an unacked message
  (worker killed mid-job) redelivers at most 3 times, then the broker
  itself dead-letters it to `invoice.extract.dead`. A poison PDF can never
  loop forever.
* Routing keys on the DLX: `retry.retry.5s`, `retry.retry.30s`,
  `retry.retry.5m`, `extract.dead`.

### Ack / nack policy (v0.9 rewrite)

| Outcome                          | Action                          |
|----------------------------------|---------------------------------|
| Success                          | ack                             |
| Transient (429/5xx/connection)   | publish DLX → retry tier (by attempt), ack original |
| Permanent (bad schema/malformed) | publish DLX → `extract.dead` + signed `status:"failed"` result, ack original |
| Unknown / no attempt counter     | discard (ack, no republish)     |
| Crash between publish and ack    | redelivery — idempotent by `job_uuid` ledger |
| Crash redelivery > `x-delivery-limit` | broker dead-letters autonomously |

## 2. Messages

### `extract.request` — Odoo outbox → worker (`invoice.extract` queue)

Published by `queue.publisher.publish_extract_request` when the drain cron
(`invoice.agent.job._drain_pending`) drains the transactional outbox.

```json
{
  "move_id": 123,
  "attachment_id": 456,
  "attempt": 1,
  "job_uuid": "9f2c…",
  "ocr_text": "INVOICE 2026-01 …"
}
```

- `job_uuid` — correlation id echoed back on `extract.started` /
  `extract.done`; generated by `account.move._enqueue_ai_job` and stored in
  `account.move.ai_job_uuid`.
- `ocr_text` — OCR already ran Odoo-side (`_cron_ocr_pending_bills`); the
  worker never touches PDFs.
- Persisted message (`delivery_mode=2`): survives broker restarts.

### `extract.started` — worker → Odoo consumer (`invoice.result` queue)

Published before the Claude call so the UI flips to a live *extracting* state.

```json
{ "job_uuid": "9f2c…", "move_id": 123, "status": "extracting" }
```

### `extract.done` — worker → Odoo consumer (`invoice.result` queue)

The ONLY result envelope. Body is the signed token; the payload never rides
in plaintext:

```json
{ "token": "<jwt>" }
```

Claims (`invoice-ai/app/result_signing.py`):

| Claim    | Value               |
|----------|---------------------|
| `iss`    | `invoice-ai`        |
| `aud`    | `odoo.invoice-agent`|
| `sub`    | `extract.done`      |
| `exp`    | now + 300 s         |
| `result` | the payload dict    |

`result` payload:

```json
{
  "job_uuid": "9f2c…",
  "move_id": 123,
  "status": "done",
  "parsed_output": { "vendor_name": "...", "lines": [...], "amount_total": 0 },
  "usage": { "input_tokens": 0, "output_tokens": 0, "cache_read_input_tokens": 0 },
  "model": "claude-opus-4-8"
}
```

Permanent failure (unparseable body): `{"status": "failed", "error": "..."}`
published and acked — never redelivered in a loop.

## 3. JWT signing rule

- Shared secret: `INVOICE_AI_JWT_SECRET` (worker) ==
  `invoice_agent.jwt_secret` (Odoo `ir.config_parameter`), HS256.
- Odoo verifies signature, `exp` (10 s leeway), `aud`, `sub` BEFORE applying
  any field. A rejected token is logged and the message acked — a poisoned
  result must never redeliver forever, and must never write data.
- Same secret family as the HTTP `/v1/extract` JWT, but separate
  audience (`odoo.invoice-agent` vs `invoice-ai`).

## 4. Ack / nack policy (worker, QoS prefetch = 1)

Canonical policy in §1 (v0.9 rewrite) — never `nack + requeue`: retries and
poison routing happen through the DLX **publish**, and the original is always
acked so the broker cannot redeliver it in a tight loop.

## 5. Odoo consumer rules

- One daemon thread per Odoo process (`post_load`), `pika.SelectConnection`,
  prefetch 10, durable queue, manual ack.
- Every result writes in a FRESH `registry.cursor()` and commits immediately —
  the thread outlives any request transaction.
- **Idempotency guard (v0.9)**: before applying a `status:"done"` result, the
  consumer runs `INSERT INTO invoice_agent_applied_job (job_uuid) VALUES
  (%s) ON CONFLICT (job_uuid) DO NOTHING` in the SAME transaction. Zero rows
  inserted ⇒ the job was already applied ⇒ the redelivered message is a
  no-op — never a second draft `account.move`. Row insert + apply commit
  together, so a crash mid-apply leaves no ledger row and the next
  redelivery retries safely.
- `status:"failed"` results (worker dead-lettered the job) mark the
  originating `invoice.agent.job` row `dead` (with `dead_reason`), flag the
  move for review, and never write extraction fields.
- Move resolution: `account.move` by `ai_job_uuid` first, `move_id` fallback.
- UNIQUE constraints backing the guard: `invoice.agent.job.job_uuid` and
  `account.move.ai_job_uuid` — double-publishing one uuid is impossible at
  the SQL layer.
